# rebuild.29：直接改写余额的原生收支处理

2026-10-18。基于公开 rebuild.28，仅重新打开金钱模块的一项合同：其它 Mod 直接改写 `V.money` 的收入和支出，也能进入游戏原生收支处理。已发布 rebuild.28 的制品和标签保持冻结。

## 对照与合同

原作者实际发行包（Release 标签 `1.20.3`，包内 `1.20.3.1`）每游戏秒观察余额，减去宏队列变化，再将未知净差额扣除并经 `money` 宏结算。它保留了直接写入兼容，但存在宏返回、异常吞掉、仅余额回滚与生命周期等边界。

rebuild.28 改为在原生函数边界处理倍率，未知改写只告警。这是按当时 observation-only 合同实现的功能缩减；现在恢复原作者要求的能力，不把旧合同下通过的检查倒记为漏报缺陷。

29 继续使用现有 `CE_moneyTransaction` 边界、Maple `onSec` 时钟、配置和模块生命周期，不接管 `V.money` 的 descriptor，不增加账本、队列、依赖或通用交易框架。

- Money Watch 开启、当前 State 有效且首个采样建立基线后，计算余额变化减去已经通过原生入口的变化。未知净额为零时不生成交易。
- 先扣除待结算净额，再通过现有 `window.money(amount, 'unknown')` 入口执行。游戏的余额不足判断、返回、异常和 `moneyStats` 更新仍由原生 `money` 完成。
- 倍率开关控制原生实际输入；监控开启但倍率关闭时，仍补原金额的账目。收入沿用收入倍率，支出沿用支出倍率，统计记录实际金额。`recordOnly` 保留原金额且不改变余额。
- 正常原生调用及其嵌套包装属于一次已处理边界，只在最外层缩放及计入余额变化。接收者、参数、返回和异常沿用既有入口。
- 基线和已处理差额只保留在当前模块内存中。读档、State 身份变化、停用及原面板重新开关会重建基线，不追补停用期间。
- 外部代码若在两次观察之间关闭又开启监控，且未调用 `CE_moneyWatch.reset()`，该短暂关闭无法被采样识别。原面板开关已接入 reset；外部脚本应使用相同接线。

## 无法区分的情况与失败边界

普通直接写入均按交易处理，无法仅从余额判断工资、退款、编辑器纠正或同 State 内部恢复。手动纠正余额前应关闭监控；已知原生读档及 State 替换由生命周期排除。

连续 `+100`、`-80` 只能补记净收入 `20`，不能重建两笔历史。直接写入与原生调用交错时，会排除原生已结算变化；发生在一次原生调用内部的额外写入归于该原生边界，不承诺分别识别。采样结算按结算时余额和配置执行，无法重现每次原写入时的余额不足判断或当时倍率。

非有限余额、差额溢出、原生入口丢失、Hook 阻止余额重建及原生异常会暂停自动补算，控制台和金钱面板提供提示。系统不盲目重试，不宣称回滚；原生执行前可能已经扣除待结算差额，执行中可能已经改变余额或部分统计。先检查余额及 `moneyStats`，处理后关闭再开启监控。更换 State 或重启也会建立新基线，不把旧失败带入新进度。

第三方或 CE Hook 的 descriptor 保持原归属。透明 Hook 可正常共存；锁值、变换等规则若阻止重建余额，则停止补算。其它 Hook 对原生结算结果的再次变换仍属其业务效果，不能同时承诺任意锁值／变换规则与完整交易效果或账目等价。

### 实际结果

- **本地**：改前的直接收入、支出／倍率关闭及混合净额用例保留失败。修订后 18 项金钱检查通过；项目 `npm run verify` 共 197 项通过，包含打包检查。两者包含关系明确，不相加。
- **现场对照**：同一卧室脚本在 28 中显示直接收入 `+100` 不生成账目，直接支出 `-100` 也不记账；原生收入仍正常。在 29 中，`+100` 以 2 倍成为余额及收入统计 `+200`；`-100` 以 0.5 倍成为余额 `-50`、支出统计 `50`；原生收入只记一次。直接 `+100`／原生 `+10`／直接 `-80` 的组合结算为实际净增 `60`、两次收入记录。该阶段 9 项检查通过。
- **原面板与保存准备**：原 Money Watch 按钮关闭及开启、停用期间不追补、故障提示、部分失败不重试、State 新建与自有原生保存等 16 项检查通过。部分失败由测试包装器在真实原生统计完成后主动抛错模拟，不称为游戏原生缺陷复现。
- **真实重启后读档**：自建样本经原生保存、真实 App 重启、原生读档后，余额和完整账目不变；随后 `+7` 直接写入结算 `+14`，且只增加一次收入记录。该阶段 6 项通过。它是 29 的专项样本，不替代此前作者旧包升级证据。
- **身份与清理**：持久安装 ZIP 摘要匹配候选，55 个普通脚本内容摘要匹配包内源码。原三个存档摘要、其它 39 个 Mod 版本、安装顺序和隐藏列表保全；自建槽位先本地归档校验，再核对 metadata 和摘要后删除，清理阶段 8 项通过。最终保留 29，真实重启回 Start，无渲染错误。

上述现场阶段分别报告，不与项目检查累计成一个通过数。验证由开发方执行，尚无本轮独立复核。未为覆盖率追加完整 Windows 或业务矩阵。

### 保留的失败与 Unknown

- 测试夹具最初使用了不存在的 RawHook 函数名，随后使用了错误的回调字段；按当前 API 改为 `RawHook.register`／`ctx.newValue`。这些是夹具准备错误，不能记为 CE 或 Dev Tools 运行缺陷。
- 安装准备脚本的占位符替换破坏了 `SHA-256` 字面量，解析失败，安装没有发生。其后一次重启仍为旧包；修正生成器并先检查语法后完成安装。
- 一次脚本身份采集早于游戏全局变量就绪而失败；明确等待游戏和 money 模块就绪后才继续。启动 ACK 不当作加载成功。
- 开始测试前场景被外部操作改变，已停止并得到独占授权。29 的核心场景通过后又出现一次非本轮发起的 PID／文档更换，原因 **unknown**；后续 UI 检查在场景前置条件处停止，重新绑定后独立建立进度。不把两段写成连续同一文档。
- 原菜单延迟绘制默认“言灵集”，首次面板断言读错目标；等待菜单稳定再打开金钱面板。另一检查误以为新进度中的监控已开启，随后显式准备开关状态。失败记录保留，未修改运行代码来迁就测试。
